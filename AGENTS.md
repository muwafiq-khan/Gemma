## Core Concept: Movie-Game-Education Hybrid

An interactive narrative experience that combines:
- **Movie** - cinematic story with plot, characters, atmosphere, emotional arcs
- **Game** — player agency, branching choices, consequences, implicit stats
- **Education** — DSA challenges embedded naturally into the story

**The key insight:** Learning is not a separate activity or reward — it *is* the gameplay. The user must solve DSA problems to progress the story, giving learning immediate purpose and emotional stakes.

---

## The Philosophy (User's Vision)

### No Retry, Story Flows Forward
- If user gets a DSA challenge wrong → the story continues on a *different* branch, not a harder one
- Wrong ≠ Game Over. Wrong = a darker turn. The character fails and the movie adapts.
- This makes it feel like a real movie — permanent consequences, no save scumming

### Purposeful Learning
- DSA concepts are never force-embedded. An agentic system decides: "Does this concept fit naturally in this scene?"
- Learning should feel like the user *needs* to learn this to survive the moment
- Not every scene has a challenge — learning happens infrequently but meaningfully

### User is the Dictator
- The user shapes major plot shifts through their choices
- The system provides a scaffolding but the user determines the path
- Non-educational choices (talk to Mary or Kathy, go left or right) are abundant — these make it feel like a game

### Personalization via Implicit Stats
Track per user session:
- Knowledge profile (per concept: correct/wrong ratio, fluency, mistake patterns)
- Character relationships (who the user sided with)
- Risk tolerance (aggressive vs cautious choices)
- Engagement signals (did they pause to learn? how many hints needed?)

These stats feed back into Gemma 4 prompts to personalize upcoming scenes.

## System Architecture Decisions

### Beats, Not Skeleton
- NOT a fixed branching tree (too rigid)
- NOT pure dynamic generation (too risky)
- **Hybrid approach:** 7-9 narrative beats as constraint anchors
- Hard points (must happen): certain character archetypes, destined events, overall arc
- Soft points (user-determined): how characters develop, which paths taken, exact dialogue
- Everything between beats is 100% dynamically generated by Gemma 4

### RAG-Powered Personalization (Active)
- Deep profile interview: movie preferences, game preferences, character identity
- Phase 1 (movie/writer/game questions) → async web search via duckduckgo_search
- Fetch 2-3 pieces of content about user's favorite writers, movies, games
- Store in `rag/{stories,movies,gaming}/`
- Gemma 4 analyzer extracts structural patterns from fetched content
- Skeleton generator uses user persona + pattern learnings together

### DSA Topic Pool
- Pre-select pool of 10-15 core DSA concepts (sorting, recursion, graphs, DP, etc.)
- An agentic system decides which subset is relevant *in context* for each scene
- Topics are not pre-assigned to scenes — Gemma 4 decides on the fly based on narrative fit

### Teaching Window
- Separate chat interface (Tab 3 in Gradio)
- When user encounters a challenge they don't know: click "Learn this concept"
- Story pauses (character finds a safe space)
- Teaching window opens with context pre-loaded: concept name, what the challenge was, user's past performance
- Gemma 4 teaches interactively
- User returns to story when ready — same challenge still there, they can attempt or skip (story moves on)

### Gemma 4 Roles (Core to the Solution)
1. **Profile Analyzer** — interviews user, builds preferences + knowledge profile
2. **Skeleton Generator** — creates story structure from genre + user profile + beat guidance
3. **Scene Planner** — before each scene, decides type (narrative/challenge/character), DSA fit, tone
4. **Scene Generator** — generates prose, choices, challenge content
5. **Answer Evaluator** — judges user solutions, provides feedback
6. **Adaptive Tutor** — teaches concepts in the learning window
7. **Ending Generator** — crafts conclusion based on accumulated stats + choices

## Key Design Principles
1. Gemma 4 is NOT a chatbot bolted on — it IS the engine (fits 30% Gemma Integration criteria)
2. The movie-game feels alive — user never sees the "rails"
3. Education has narrative purpose — not "learn this because the syllabus says so"
4. Failure is narrative, not punitive — wrong answers create different stories, not dead ends
5. The user feels like the protagonist, not a student

## Critical Rule: Never Execute Without Permission
**No code writing, file creation, package installation, or any execution happens without the user explicitly saying "go" or "build it." Planning and discussion only until given the green light.**

## Critical Rule: Never Deviate Without Asking
**Whenever I plan or decide something even slightly different from what the user said, I must explicitly ask for permission first. If I'm unsure how to implement the user's intent, I ask before acting. No assumptions.**

## Protocol: PLAN/BUILD Prefixes
- User starts a message with **PLAN:** → discussion only. No execution, no file changes, no commands.
- User starts a message with **BUILD:** or **GO:** → execute allowed.
- When agent proposes a plan, user must reply with exactly **"Build"** (greenlight) or **"Revise"** (continue planning). Any other response = wait for clarification.

## Critical Rule: Never Break Existing Functionality
When modifying any file, you MUST verify that existing features still work. After every change:
1. Run `python -m py_compile` on all modified files to check syntax
2. Trace through the code flow to ensure old event handlers still fire, old state fields are still populated, and old UI interactions still work
3. If you change the event-bridge mechanism (how HTML clicks talk to Python), test both directions: DOM click → JS → Gradio event → Python handler
4. Never assume a component renders when `visible=False` — Gradio 6 uses Svelte `{#if}` conditional rendering, so hidden components don't exist in the DOM at all. Use CSS hiding instead (`visible=True` + `position:fixed;left:-9999px`)
5. For Gradio JS→Python bridges, prefer `gr.Textbox(visible=True)` with CSS hiding over `visible=False`


## Track Folder Protocol

Every agent MUST follow these rules in EVERY response:

### 1. Track Log (`track/track.md`)
- After EVERY action (success or failure), write a 5-line summary.
- Format: What happened, result (fix/fail/why), key context, internal flow (how you approached it), jargon explainer if needed.
- Keep it short — 5 lines max, easy to understand.

### 2. Critical Updates (`track/critical.md`)
- Agent NEVER writes here without user permission.
- If something feels critical (major fix, architecture change, root cause), ask user first.
- If user says yes, write in broad terms: what happened, what you tried, success/failure, your thought process, internal flow in plain language.
- If heavy jargon exists, write it AND provide a plain-language explainer right after.

### 3. Fixes (`track/fixes.md`)
- Log every fix: what broke, which file, what the fix was.
- Keep it factual and brief.

### 4. Bug Report (`track/bug_report.md`)
- Track known bugs: ✅ FIXED or ❌ NOT YET FIXED.
- When investigating a bug, read the codebase to confirm status — don't trust old entries blindly.
- Update with evidence (file:line references) of what you found.

### Writing Style Rules
- Write like you're explaining to another human, not a machine.
- If you must use a technical term, write it AND follow with a short plain-language explainer.
- Example: "JS bridge (the JavaScript code that sends clicks from the webpage to Python) was broken."
- No vague writeups. Be specific about what happened, where, and why.
- When investigating whether a bug is fixed, do NOT rely on reading the current code alone. Use `git diff` or `git log` to compare against previous commits — this proves whether a fix actually landed vs just looking like it did.

## Terminal Output Access
The agent has NO way to see the user's terminal in real-time. User should run the app with logging:
```
python app.py 2>&1 | tee app.log
```
This writes ALL terminal output (prints, errors, tracebacks) to `app.log` while still showing on screen. The agent reads `app.log` to see errors, debug prints, and Python tracebacks using `Get-Content app.log -Tail 50` or `Read` tool.

**Rule:** Whenever the user reports an error or something not working, the agent MUST immediately read `app.log` FIRST before asking any questions or making changes. Do not wait for the user to tell you to check the log — check it automatically on every error report.

## Build-Test Steps (Build Small → Test → Proceed)

**Step 1: Web Search Ability**
- Create `rag/` folder structure + `rag/fetcher.py`
- Uses `duckduckgo_search` + `requests` to fetch content based on user's mentioned movies/writers/games
- Store fetched content as `.txt` files in `rag/{stories,movies,gaming}/`
- Wire into existing flow: after profile interview completes, extract names and fetch
- **Test:** Run app, complete interview, verify files appear in `rag/` folders

**Step 2: Redesigned Interview + Full RAG Fetch**
- Rewrite `prompts.py` — 2-phase interview (Phase 1 = movie/game trigger fetch, Phase 2 = character identity)
- Rewrite `state.py` — rich nested user_profile structure
- Update `app.py` — Phase 1 → async fetch → Phase 2 → wait → proceed
- Fetcher runs for ALL categories
- **Test:** Full interview → rag/ has files for all three subfolders

**Step 3: Pattern Analyzer**
- Create `rag/analyzer.py` — reads rag/ content, calls Gemma 4 with pattern_extraction_prompt
- Structured patterns stored in `state["rag_patterns"]` (session-level derived data, NOT inside user_profile — profile is static interview data; pattern learnings are fed to skeleton/scene prompts as a separate input)
- **Test:** Inspect printed pattern JSON for quality

**Step 4: Enhanced Skeleton**
- `skeleton_prompt()` receives pattern_learnings_json
- Skeleton generated using persona + structural patterns
- **Test:** Compare skeleton before/after patterns
